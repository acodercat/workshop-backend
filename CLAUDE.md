## Commands

```bash
# Install / sync deps
uv sync

# Dev server (API on :8005, root_path="/api/v1")
uv run uvicorn app.public_main:app --host 0.0.0.0 --port 8005 --reload

# Admin console — a THIRD ASGI app in its own process (root_path="/admin/api/v1").
# Bind to a private interface: every route can change money or account state and
# the public gateway must have no route to this port. scripts/deploy.sh does not
# manage it yet — start it by hand.
uv run uvicorn app.admin_main:app --host 127.0.0.1 --port 8006 --reload

# Staff accounts are provisioned out of band (no self-registration, no invite):
STAFF_PASSWORD='...' uv run python -m scripts.manage_staff \
  --create --username=alice --name="Alice"

# Background process (separate from the web server; runs the credit-settle
# sweeper + subscriber, the payment reconciler, the scheduled-task
# dispatcher, and — behind its own flag — the mid-turn budget enforcer
# (``budget_enforcer_enabled``)). Run alongside the API in its own terminal:
uv run python -m app.workers.run

# Production — single-host manual deploy via scripts/deploy.sh. Top-level
# commands act on BOTH siblings (web + background):
bash scripts/deploy.sh deploy       # stop both + uv sync + alembic upgrade + start both
bash scripts/deploy.sh restart      # code-only restart of both (no deps / no migration)
bash scripts/deploy.sh status       # report state of BOTH web (:8005) and background
bash scripts/deploy.sh logs         # tail -f logs/uvicorn.log
bash scripts/deploy.sh background start|stop|restart|status|logs   # the background process alone
# Web truth source is ``lsof -t -i:8005``; background's is ``pgrep -f 'app.workers.run'``
# (no port). Neither uses a PID file, so both tolerate instances started
# outside the script. uvicorn stdout → logs/uvicorn.log, background stdout →
# logs/background.log; loguru/stdlib app logs go elsewhere under logs/ per
# app/logging_config.py. Multi-node: run both processes on every host —
# the settle sweeper self-elects one active poller via a Postgres advisory lock.

# HTTPS / custom port — script's defaults won't fit; use uvicorn directly:
uv run uvicorn app.public_main:app --host 0.0.0.0 --port 9090 --workers 1 \
  --ssl-certfile ./cert/<domain>.pem --ssl-keyfile ./cert/<domain>.key

# Migrations
uv run alembic upgrade head
uv run alembic revision --autogenerate -m "description"

# Tests (pytest; asyncio_mode is project-level "auto" — no @pytest.mark.asyncio needed)
uv run pytest tests/                       # ~660 offline unit tests (tests/*.py) — no DB/Redis/network
# Checks — the same three CI runs, in the same order
uv run ruff check .                           # lint (F, E7, E9, I, UP)
uv run ruff format --check .                  # formatting
uv run mypy                                   # types (scope in [tool.mypy])
uv run pytest tests/test_credit_settle_usage.py::test_name
# tests/*.py (unit) run with no external deps; tests/e2e/ is opt-in (see below)

# If five modules fail at COLLECTION with "Unknown scheme for proxy URL
# socks://…", that is the shell's ALL_PROXY, not the code: the httpx
# AsyncClient those tests build at import time reads it and httpx has no
# SOCKS support without the socksio extra. Unset it for the run:
env -u ALL_PROXY -u all_proxy uv run pytest tests/

# Full-pipeline E2E (opt-in; needs backend + worker + Redis + Postgres + sandbox running)
RUN_E2E_TESTS=1 uv run pytest tests/e2e/ -v
```

`alembic/env.py` imports `app.models.*` and `config.settings` — migrations rely on `db_uri` from `.env` at repo root.

**The migration history is not squashed, and that is a decision.** Ninety-plus files is slow to replay on a fresh database and holds plenty of steps a later one undid, but collapsing the early ones into a single initial revision is only correct if **every** live database is already at or past the collapse point. One that is not — an unattended staging box, a colleague's local, a restored backup — meets a `down_revision` it has never heard of and stops, or worse, runs `CREATE TABLE` against tables that exist. Squashing is therefore gated on reading `SELECT version_num FROM alembic_version` on every live database and choosing a point at or before the oldest, and it is worth doing only when there are no pending migrations to complicate the answer. The gain is developer-setup time; nothing about it reaches production behaviour.

## E2E tests (`tests/e2e/`)

Opt-in via `RUN_E2E_TESTS=1` (mirrors axon's `RUN_INTEGRATION_TESTS`).
Each test drives the real production pipeline through the public HTTP
API: create session → POST message → consume the per-session SSE
stream until `agent.stopped` → verify the persisted state via
`GET /sessions/{id}` → `DELETE /sessions/{id}`.

Preconditions before running:

- Backend dev server up on `:8005` (or override via `BACKEND_BASE_URL`).
- Agent worker running (`cd ../agent-worker && uv run python -m agent_worker`).
- Postgres + Redis + OpenSandbox reachable per the worker's `.env`.
- Worker's `models.toml` has the model id the test's tier resolves to —
  the e2e test creates a session with the default `STANDARD` tier, which
  `settings.session_tier_models` maps to a concrete model id; make sure
  that id exists in `models.toml`, or adjust the tier map.

The `test_user` fixture in `tests/conftest.py` provisions a unique
throwaway user via raw psycopg (no public registration endpoint exists
by design) and tears down everything that user owns regardless of
pass/fail: cascades through `user → session → message + session_turn`,
plus an explicit `sandbox` sweep keyed on session_id (the sandbox
table is application-managed without a session FK on purpose). One
full happy-path run takes ~15-30s wall time and a few cents of LLM
tokens; sandbox containers spun up during the test get cleaned up by
the OpenSandbox reaper, not by this fixture.

## Architecture

### Request topology

The backend and worker **never talk directly**. Postgres `session_turn` is the queue **and** the ownership truth source; Redis carries only the wake signal and the SSE output stream:

- Backend INSERTs a `session_turn` row (status `PENDING`) and publishes on `notify:worker` (Pub/Sub) to wake the worker. The Postgres row — not Redis — is the queue.
- Worker claims the row (`FOR UPDATE SKIP LOCKED` under a DB-lease `worker_id`), runs the agent, and XADDs events to `session_stream:{session_id}` (Stream). On terminal it writes `session.status` + the assistant `message` directly into the backend's tables in one fenced transaction.
- Backend's `GET /sessions/{id}/stream` XRANGEs (replay) then XREADs (follow) that stream and forwards each entry as SSE.

Redis key/channel names in `app/services/redis.py` (`SESSION_STREAM_PREFIX`, `WORKER_NOTIFY_CHANNEL`, `USER_EVENTS_CHANNEL`, `CANCEL_CHANNEL_PREFIX`, `SETTLE_NOTIFY_CHANNEL`) are a **wire contract** mirrored in `agent-worker/agent_worker/wire/keys.py`. Changing one without the other silently desyncs the services.

### State split: DB vs worker

- **DB is rendering state.** `message.blocks` (JSONB) holds the structured block list the frontend renders. USER rows are inserted in `queue_user_message`; ASSISTANT rows are projected from worker events (the worker writes them — backend does not synthesize assistant rows).
- **Worker owns LLM state.** Conversation history / compacted context is the worker's concern — the backend enqueues only `{session_id, query, files}` and deliberately does **not** send history. The serialized axon `Message` list now persists in the backend-migrated `session_context` table (see below), but only the worker reads/writes it; the backend just owns its schema.
- `session.status` (`app/models/session.py`) has five values across three layers: `IDLE` (initial, stamped by `create_session` on a fresh row — the worker never writes it), `RUNNING` (backend flips here the moment a turn is enqueued), and one of three terminals — `COMPLETE` / `CANCELLED` / `FAILED` — written by the worker atomically with the assistant insert (or with no row, on the error path). The frontend uses this to decide whether to open the SSE stream; gates elsewhere check `== RUNNING` / `!= RUNNING`, not a terminal set.
- **The worker is the sole writer of a terminal status, with exactly two documented exceptions**, both in `app/services/session/recovery.py` and both for holes no worker can cover. `fail_abandoned_turn` handles the entire fleet being down (or a turn never claimed): the session would otherwise pin `RUNNING` forever — `DELETE` 409s, new messages 409, cancel pub/sub reaches no one — and the worker's own `expire_stale_turns` cron can't help because it only runs while a worker is alive. It fires from the **credit sweeper** (the one background process guaranteed to keep running) once a reservation has sat OPEN past its `expires_at` — the "worker is definitively gone" signal — and is composed *into* the sweeper's refund transaction so money and lifecycle reconcile atomically. `cancel_unclaimed_turn` is the same mechanism turned at a user who presses stop while their turn is still `PENDING`, where the cancel endpoint's pub/sub signal reaches nobody. Neither is a general-purpose backend write path: do not add a third without the same "no worker can do this" justification.
- A new session carries four creation-time, immutable columns. The client picks a **capability tier** (`tier ∈ {FAST, STANDARD, ADVANCED}`, default `STANDARD`) — never a model name; `create_session` resolves it to `session.model_id` via `settings.session_tier_models` (validated against `settings.supported_session_model_ids`). It also stamps `agent_type ∈ {FULL, LITE}` (sandbox agent vs Q&A+web-search, default `FULL`) and `thinking` (extended-reasoning toggle, default on; shown to users as "deep think"). `tier` / `agent_type` round-trip to the UI; `thinking` and `model_id` do not. The worker selects its actual LLM from its own config keyed by `model_id`, **and** the backend reads `model_id` for the credit rate card at reserve time (`app/services/credits/rates.py`) — a `model_id` absent from `settings.credit_rates` makes the reserve fail, so the column is load-bearing, not an audit field.
- **Soft-delete**: `DELETE /sessions/{id}` sets `session.deleted_at` rather than removing rows (returns 409 while `status == running`). Every read folds `deleted_at IS NULL` into its `session_id`-scoped filter, so a soft-deleted session reads as gone (and its id isn't leaked) while child rows + the credit_reservation back-link are retained. The delete handler settles the session's open reservation first.
- **Pinned sessions list first.** `session.pinned_at` (NULL = not pinned) orders `GET /sessions`: pinned ones first, the most recently pinned on top, then the rest by `updated_at` — under every filter (`search`, `project_id`) too. `PATCH /sessions/{id}` takes `pinned: bool` (`app/services/session/pinning.py`); a request that sends nothing but `pinned` keeps `updated_at` (set to itself, as `_moved_out` does), since pinning is not activity and an unpinned session would otherwise jump to the top of the recent ones. Re-pinning a pinned session keeps its place. At most `MAX_PINNED_SESSIONS` (10, `session_pin_limit`): the client lists every pinned session in a sidebar group that does not scroll.

### `session_context` table (`app/models/session_context.py`)

The worker's serialized agent memory, **worker-touched / backend-migrated** (same ownership split as `session_turn` and `sandbox`: backend owns alembic, worker owns the rows — written via raw SQL in `agent_worker.infra.session_context_repository`, never read or written by the backend). 1:1 with `session` (PK = `session_id`, `ON DELETE CASCADE`). Holds the axon `Message` dicts (`messages`) — compaction state, provider-opaque thinking signatures, `preserve_in_compact` flags — that the projected `message` table (UI blocks) can't round-trip, plus `model_id` (provider pin / audit, mirrors `session.model_id`) and `todos` (the durable todo checklist). `todos` is a **separate column on purpose**: `todo_write` calls are compactable out of `messages`, so the list gets its own non-compactable home; the worker rewrites it each turn from `Agent.todos` and reseeds via `Agent.run(todos=...)`. `project_snapshot` (nullable) is the project as the agent was last told it — id, name, an instructions digest, each file's id — which the worker reads at claim to remind the agent only of what changed, and writes with `messages` so the two commit or roll back together. This table replaced the worker's former on-disk `{sessions_dir}/{session_id}.json`, so a session resumes on any worker replica.

### Sandbox table (`app/models/sandbox.py`)

One row per OpenSandbox container, **worker-managed** — the backend only declares the schema (so worker-touched columns ride in backend migrations) and sweeps the table on test teardown. **No DB-level FK to `session`** (avoids CASCADE footguns and constraint cost on the worker's hot insert path); reads and cleanup key on `session_id` directly. Multiple rows accrue per session: the worker never kills a container (it only `close()`s the HTTP client, leaving it warm for the next turn) — a **separate reaper process** kills containers idle past a `last_used_at` threshold or whose session is soft-deleted, then flips the row terminal. The active sandbox for a session is its most-recent non-terminal row; terminal rows are never deleted. The status enum and the reaper's transient claim state are documented in the model docstring.

### SSE streaming (`app/services/session/streaming.py`)

Two-phase generator: replay all existing stream entries, then block-read until an `agent.stopped` terminal event arrives. An older version merged `message_chunk` events into one blob on replay and lost tool calls — do not reintroduce that. Cold history is served by `GET /sessions/{id}` (structured `blocks`), not by the SSE endpoint; the stream endpoint is only meaningful while `status == "running"`.

### Per-user notifications `/me/events` (`app/services/user/hub.py`)

Separate from `session_stream`: a lightweight SSE feed carrying idempotent `session.status_changed` for cross-tab sidebar sync. **One Redis `SUBSCRIBE` per process** (the `UserEventHub`, started in the lifespan) fans `user_events:bus` out in-memory to each connection's bounded `asyncio.Queue` — opening `/me/events` allocates a queue, **never a Redis connection**. At-most-once (Pub/Sub) is fine because the payload is idempotent state sync; no replay, no sticky sessions, multi-node native. `USER_EVENTS_CHANNEL` is a wire contract mirrored in the worker — deploy together. Both sides publish it: the worker for the terminals it writes, the backend (`publish_session_status` in `app/services/user/events.py`, best-effort, after commit) for the transitions it writes itself — `RUNNING` at enqueue, and the `CANCELLED` / `FAILED` of the two recovery paths. Full design: [`docs/user-events-fanout.md`](docs/user-events-fanout.md).

### Redis client setup (`app/public_main.py` lifespan)

Two pools, intentionally separate (see `_make_redis_client`):

- **Short-op pool** (`app.state.redis`) — `BlockingConnectionPool` sized by `redis_pool_size` (default 30). XADD, PUBLISH, DELETE, PING. When full, callers wait up to `redis_pool_timeout_seconds` for a connection before raising — trades a tail-latency spike for fewer 5xx during bursts.
- **Streaming pool** (`app.state.redis_streaming`) — plain `ConnectionPool` sized by `redis_streaming_pool_size` (default 100). Holds one connection per active SSE for the full XREAD `block_ms`. Fail-fast on full, because hitting the cap means the box is at its SSE capacity — back-pressure is the right answer.

Sharing a single pool would let SSE long-polls starve short-op traffic. Both pools probe checked-out connections on the 30s `health_check_interval` so a silently-dropped socket surfaces promptly.

Startup uses `_ping_db` / `_ping_redis` with exponential backoff (`startup_probe_*` settings) so a few-second dependency race at boot doesn't crash-loop the pod. Liveness (`/health/live`) is always 200; readiness (`/health/ready`) returns 503 when DB or Redis are unreachable so K8s stops routing to the pod without restarting it.

### Observability (`app/observability.py`)

`install_observability(app)` (called once in `app/public_main.py`) wires three additive, backend-optional concerns — all no-ops until their backend is configured:

- **Request-id correlation** — `RequestIDMiddleware` reuses a sane inbound `X-Request-ID` (validated against `_REQUEST_ID_RE`, else minted) and binds it into the loguru context so every log line carries `request_id`, echoing it back in the response header. Implemented as **raw ASGI**: it only touches the response-start message, so streamed SSE bodies pass through untouched.
- **Sentry** — no-op until `sentry_dsn` is set (`sentry_environment`, `sentry_traces_sample_rate` knobs).
- **Prometheus** — `/metrics` endpoint (gated by `metrics_enabled`, default on) via `prometheus-fastapi-instrumentator`, with `/metrics` + both health probes excluded from its own histograms.

### Enqueue ordering (`app/services/session/enqueue.py`)

`queue_user_message` has a load-bearing sequence:
1. `SELECT ... FOR UPDATE` the session row (`deleted_at IS NULL` in the predicate). Reject 409 (`GenerationInProgressError`) if `status == RUNNING`; raise `SessionNotFoundError` → 404 if the row is gone (a `delete_session` committed in the window). The lock serializes concurrent enqueues **and** `delete_session` (which takes the same lock before tombstoning). If the send carries `agent_type` (the one-way LITE→FULL mode upgrade — the composer's mode pick is local until the user sends), apply it here under the lock so the flip commits atomically with the turn; FULL→LITE rejects 400 (`AgentTypeDowngradeError`). One of two `agent_type` mutation paths, both applying `upgrade_agent_type` (`app/services/session/agent_type.py`) under the session row lock; the other is moving a session into a project (`PATCH /sessions/{id}`).
2. Lazy-sweep this user's open credit reservations into terminal state.
3. Bind uploaded files (`_bind_session_files`, which HEADs each new object in OSS for its true size) — **before** the reservation, so that round trip never holds the user-row lock.
4. INSERT the `session_turn` (status `PENDING`) and flush for its auto-generated `turn_id`. Besides the user's text and the skill / Connector snapshots, the row carries `reminders`: model-facing strings a **server-side** caller rendered (today only the schedule dispatcher), which the worker appends verbatim to `Agent.run(reminders=...)`. No request schema carries this field — client text never reaches the model as a system reminder. The row also carries `timezone` (nullable): the IANA zone the client reported in `MessageCreate.timezone` — kept only if `app/common/timezones.py` knows it, and dropped rather than refused otherwise, so a message is never turned away over it. The worker's `create_schedule` tool schedules in it — the worker INSERTs the `schedule` row itself, mirroring `POST /schedules`' caps and first-run computation (`agent_worker/infra/schedule_repository.py`, `domain/schedule.py`; change both repos together) — and registers that tool only for a turn that has one, so a scheduled run (enqueued server-side, no zone) can never schedule a task of its own.
5. Reserve credits — raises `InsufficientCreditsError` → 402 if the estimate would push the balance negative; the whole tx rolls back (no message, no turn).
5a. **Concurrent-task cap**: reject 429 (`ConcurrentTaskLimitError`) if the user already has `settings.max_concurrent_running_tasks` (default 10) sessions in `RUNNING`. Enforced right after reserve so it runs under the reservation's user-row `FOR UPDATE` lock — concurrent enqueues for the same user serialize on it, so the count can't overshoot; a reject rolls the whole tx back.
6. INSERT the user `message`, flip `status = RUNNING`, then DELETE the previous turn's `session_stream:{id}` — all before one commit. The stream DELETE is **last, after every fallible step**, so a 402/skills failure can't wipe replay history for a turn that never enqueues; before the commit so the stream is clean before the worker (woken post-commit) writes the new turn's first event. Best-effort, like `publish_wake`: a Redis outage must not refuse the message, and a stream left behind is harmless because the SSE reader drops entries stamped with another turn's id.
7. `publish_wake` on `notify:worker` **after** commit (so the worker's claim sees the row). Best-effort: a missed publish just costs one worker poll cycle and never raises into the handler.

### Events wire format (`app/common/event_types.py`, `app/common/sse.py`)

`EventType` enum is the backend's independent copy of the strings the worker emits (`agent_worker/wire/session_events.py` — the `SessionEventEmitter` — is the authoritative producer). The backend has no runtime dependency on axon; it only consumes the stream. Redis Streams store `str → str` only, so structured fields (`args`, `files`, `usage`) arrive JSON-encoded and are forwarded **verbatim** to the frontend. A `None` field is dropped by the worker's `_encode_fields` rather than written, so a consumer treats an absent field and a null one the same.

### Auth

JWT (`app/auth.py`), bcrypt passwords hashed/verified off the event loop (`asyncio.to_thread`). Identity is `username` (the auto-generated `axon_${id}`) + `email` + `phone` (both nullable, both `UNIQUE`; a user has whichever channel(s) they registered/verified through); sign-in is username+password (`POST /auth/access-tokens`) or the email-**or-phone** OTP flow below. Revocation is by bumping `user.token_version` — tokens carry the version they were issued against; `_decode_and_get_user` rejects tokens whose version is stale. `revoke_user_tokens` runs after a password, email, **or** phone change (phone is a login + recovery vector, so rotating it invalidates stale tokens the same way). SSE endpoints authenticate with the **header** Bearer token via `authenticate_for_streaming`, which opens a short-lived DB session for the JWT lookup and closes it before the stream begins (so the SSE lifetime doesn't pin a DB connection) — the frontend uses `@microsoft/fetch-event-source`, which can set headers. **Three JWT classes, all defined in `app/auth.py` on purpose** — they are defined by their mutual exclusion, and that is only auditable if the decoders sit next to each other. User access tokens carry **no** `scope`; **share-view tokens** carry `scope=share-view` (see Sharing); **staff tokens** carry `scope=staff` (see Admin console). `_decode_and_get_user` rejects anything *with* a scope, each scoped decoder rejects anything without *its* scope, so no class can cross over. Every decoder fails closed, returning `None` on bad signature / expiry / wrong scope / ill-typed claims alike so the caller raises one indistinguishable 401.

### Registration / verification — email + phone (`app/services/auth/`, `app/services/email/`, `app/services/sms/`)

The 6-digit-code flow is **channel-agnostic** (`app/services/auth/verification.py`): every request carries `channel ∈ {email, phone}` plus an `identifier` (the email address or the China-mainland mobile number). Only the **send step** differs — `email` renders an HTML template and dispatches via **Alibaba DirectMail** (`app/services/email/`); `phone` texts via **Aliyun SMS** (短信服务 / dysmsapi, `app/services/sms/`, one seam `send_verification_sms`). The Redis code lifecycle (TTL, resend cooldown, wrong-attempt cap) is identical across both. Phone numbers are normalized to canonical storage form by `app/common/phone.py` (`NormalizedPhone`, strips spaces/dashes, validates `1[3-9]` + 11 digits) before use as a login key.

**Login and registration are separate flows** over that shared dispatch (`POST /auth/verification-codes`, body `{channel, identifier}`). **Login** (`POST /auth/access-tokens-by-code`) is login-only: peek-verify the code, then an existing `ACTIVE` user → consume + issue a JWT (`kind="logged_in"`); an unregistered identifier → `not_registered` (404), steering the client to register. **Registration** (`POST /users`) is **invite-gated**: the body carries an `invite_code`, and a valid invite *is* the access grant, so the user is created `status=ACTIVE` (auto-generated `axon_${id}` username + random password placeholder) and gets a JWT immediately (`kind="logged_in"`, same `LoggedInResponse` as login) — there is no admin-approval/`PENDING` gate. Registration also mints the user's own personal referral code and records the redemption. Invite codes (`app/services/auth/invite.py`, `invite_code` + `invite_redemption` tables) come in two origins: `SYSTEM` (operator-issued via `scripts/create_invite_code.py`, seeds the cold start) and `REFERRAL` (per-user, capped at `invite_referral_max_uses`); the slot is fence-claimed (`claim_invite`, an atomic `UPDATE … WHERE used_count < max_uses … RETURNING`) **before** the OTP burn so an exhausted code never strands a verified code. A successful referral credits the referrer `invite_referral_reward_credits` (default 500, a `REFERRAL` ledger row) best-effort in its own transaction, alongside the welcome credit grant. State for in-flight codes lives in Redis (TTL = `register_code_ttl_seconds`, default 600). Per-email resend cooldown (`register_code_resend_cooldown_seconds`, default 60) and per-code wrong-attempt cap (`register_code_max_attempts`, default 5) are layered with per-IP rate limits on the endpoints themselves. DM/SMS creds default to empty so dev boxes without provider access still boot — calls that need them fail loudly at send time, not at startup. **`credential_change.py`** reuses the same code-verification primitive (namespaced `email_change:{user_id}:{addr}` / `phone_change:{user_id}:{num}`) for changing a signed-in user's email or phone, one channel-parameterized flow for both: a two-step *sudo-gated* flow (`POST /me/email/verification-codes` → `PUT /me/email`, and the `/me/phone/...` mirror in `app/api/public/user.py`) that confirms identity, pre-checks uniqueness on the new value, sends a code to it, then atomically swaps the column and bumps `token_version`. **The sudo gate** (`require_sudo` in `app/services/auth/sudo.py`, `SudoProof` in `app/schemas/user.py`) fronts all three credential changes — password, email, phone — and takes exactly one of `current_password` or `verification_code`, a sudo code sent by `POST /me/verification-codes` to an address the account already has (`sudo_code:{user_id}`). The code is load-bearing, not a convenience: OTP registration stores a random placeholder password the user never sees, so a password-only gate left every OTP-registered account unable to change anything.

### Rate limiting (`app/rate_limit.py`)

slowapi, **keyed on the authenticated principal when present, else the client IP** (`_rate_limit_key`: the auth dependencies call `set_rate_limit_principal(request, kind, id)`, which FastAPI resolves before a decorated limit reads the key — so an authenticated endpoint's own limit is immune to NAT/CGNAT-shared IPs, while pre-login endpoints still key on IP). `kind` namespaces the two id spaces — `user:{id}` for customers, `staff:{id}` for console operators — and namespacing happens in that one function, so no call site pre-formats a key and none can end up prefixed twice. **Counters stored in Redis** (`storage_uri=settings.redis_url`) so the limit is a true cluster-wide ceiling rather than per-uvicorn-worker (an in-memory store would make `5/minute` effectively `5 × workers` and reset on restart). Degrades gracefully if Redis is down — `in_memory_fallback_enabled` keeps counting locally and `swallow_errors` ensures a storage blip never 500s a request. Limits are config knobs (`rate_limit_*` in `config.py`): `login` 5/min, `message_create` 30/min, `share_unlock` 5/5min, `register_code` `3/minute;20/hour` (layered burst + hourly per OWASP OTP guidance — a `;`-separated multi-limit string slowapi enforces in full), `register` 20/hour, default 200/min. That principal keying holds for **decorated** limits only: the global floor (`rate_limit_default`) is applied by `SlowAPIASGIMiddleware` before any dependency runs, so it always keys on the IP and is sized as a floor. `RateLimitExceeded` is registered as an exception handler in `app/asgi.py`; the ASGI middleware (not `SlowAPIMiddleware`, which falls back to slowapi's flat body for an async handler) is what makes a floor 429 carry the same envelope. If abuse appears, raise the limits behind authenticated identity rather than the per-IP key (NAT'd corp networks otherwise hit the cap collectively).

### Admin console (`app/admin_main.py`, `app/api/admin/`, `staff` + `admin_audit_log` tables)

**Status: live on dev, not yet deployed.** Migration `c4a91f7d20b3` is applied, operator accounts exist, and both processes run locally (`:8006` API + `frontend-admin` on `:3400`). Production is still a manual runbook — `deploy.sh` has no admin sibling. Current surfaces: staff, users + credit adjustments, sessions, feedback triage, message ratings, invites, skills (list, upload, edit, toggle), connectors + catalog (add/edit/publish), payments, the credits/revenue/check-in dashboard, and the audit browser. The UI is bilingual (zh-CN / en-US) on next-intl, same stack and cookie as ppig; `npm run check:i18n` pins catalog parity. See [`docs/admin-console.md`](docs/admin-console.md) for each surface's routes, the load-bearing decisions, and the going-live runbook.

The internal operations surface: **a separate bounded context, not a separate service**, and the split runs along two independent axes.

**Code and schema are shared.** Admin endpoints import `app.models` / `app.services` / `app.database` directly and admin tables ride in the same alembic history. A second service against the same DB would guarantee model drift and — worse — would have to re-implement the funnels that hold the money invariants (`credits._internal`, `commission._internal`, `payment.orders`). So admin code is a **sub-namespace inside each existing layer**, not a vertical slice: `app/api/admin/`, `app/schemas/admin/`, `app/services/admin/`, with `staff`/`admin_audit_log` living in `app/models/` like any other table and the staff token class in `app/auth.py` beside the two it must stay exclusive with.

**The runtime surface is not shared.** `app/admin_main.py` is a third ASGI app (`app.admin_main:app`) in its own process (`root_path="/admin/api/v1"`, conventionally `:8006`) — the public API never mounts an admin route and vice versa. Both apps are built by **`app/asgi.py:create_app`**, which owns the limiter, error handlers, middleware *order*, CORS, observability and the health probes; the four arguments it takes (`root_path`, `cors_origins`, `lifespan`, `readiness_probes`) are the complete list of what differs between the two surfaces, and nothing else may. The console's differences: no Redis client on `app.state` (no SSE, no enqueue — slowapi still counts in Redis via its own `storage_uri`, so limits stay cluster-wide, which is also why readiness probes the DB only), no startup dependency probe (an internal tool is better served by a 503 on the first request than a crash-looping process), and its own CORS allowlist (`admin_cors_origins`). **Security is a deployment property**: bind to a private interface / VPN; nothing in the code enforces it.

Two rules bind everything admin:

1. **Never write a column that carries an invariant except through its owning service.** Money, lifecycle and anything with a rule to keep goes through the service that owns it — if none exists, add one under `app/services/` rather than issuing the UPDATE from an endpoint. An invariant-free column (a user's `status`, a feedback row's triage state) may be assigned inline, inside `audit()` like every other write. `app/services/admin/` holds only what no other module owns (the audit funnel, staff accounts).
2. **Every mutation commits through `app.services.admin.audit`**, an async-context-manager unit of work that writes the audit row and owns the commit:

   ```python
   async with audit(
       ctx,
       action=AuditAction.STAFF_UPDATE,
       target_type="staff",
       target_id=account.id,
   ) as draft:
       await staff_service.update(ctx.db, account, status=body.status)
       draft.payload = changes  # before → after, filled in inside
   ```

   This is structural, not a convention: the mutation does not persist unless it happens inside the block, so an endpoint cannot forget to audit — it can only fail to save. A raise inside the block commits nothing, so a failed action leaves no row claiming it happened. **Never commit inside the block** (that re-splits the two into separate transactions); flush instead, which is how a create gets its id for `draft.target`. Credential-shaped payload keys are redacted as a backstop.

**Vocabulary is named, storage is not**: `AuditAction` (`app/services/admin/actions.py`) is a Python StrEnum over a plain VARCHAR column — adding a member needs no migration, but a typo won't compile and the audit browser's filter has a list to offer. It carries **only what the console can do today**; land the slice, then add the member. Targets are plain `target_type` / `target_id` strings — no wrapper types.

**Authn and context**: `app.auth.authenticate_and_get_staff` answers "who is calling"; `app/api/admin/dependencies.py` packages the result as **`StaffContext`** (db + operator + request id + caller IP), the only way into an admin endpoint. **There are no roles** — every active operator has full console access (v1 decision, `docs/admin-console.md`); accountability comes from the audit trail, and `dependencies.py` is where a role gate would return if tiers are ever needed. `staff` is a **separate table from `user`**, never an `is_staff` flag: operator identity isn't customer identity, credentials/revocation are independent, and `organization_member.role` is *tenant*-scoped — nothing to conflate with platform staff. Sign-in is the one endpoint that can't use `StaffContext` (it learns who the operator is by checking the password) and calls `build_context` directly so its `staff.login` row carries the same metadata; a *refused* sign-in stays uniform outside (one 401, `staff_invalid_credentials`) but logs a warning naming the target and the withheld cause.

**`app/api/admin/staff.py` is the reference slice** — every future console feature copies its shape (`StaffContext` in the signature, mutation inside `audit()`, invariants in the service, plain reads inline). The service layer holds the rules the endpoint has no business re-deriving: a password change signs that account out everywhere, and **the console never loses its last `ACTIVE` account** (409 `staff_last_active`) — checked *after* a status change is flushed, with the active rows locked `FOR UPDATE` *before* it, in id order, so two operators disabling each other queue rather than deadlock and the second gets the typed refusal. No self-registration, no OTP, no invite: accounts come from `scripts/manage_staff.py` (password via `STAFF_PASSWORD` env so it never hits shell history or `ps`), which drives the *same* service module rather than duplicating it, and is the recovery path for a fully locked-out console. Script runs write no audit row — `staff_id` is `NOT NULL` and a script has no operator to attribute; they're authorized by DB credentials instead.

`app/services/admin/` imports **no FastAPI** — the HTTP layer builds `AdminContext` (pure data) and the services only read it, which is what makes the audit funnel testable without fabricating a `Request`.

`RequestIDMiddleware` writes the correlation id to the ASGI scope state as well as the loguru context, precisely so `admin_audit_log.request_id` can persist it as a value.

### Sharing (`app/api/public/share.py`, `session_share` table)

A session owner mints a share record with a password. Recipients hit a public unlock endpoint that swaps the password for a short-TTL **share-view token** (`share_view_token_expire_minutes`, default 15) — a JWT bound to that share, distinct from a normal user access token. The session's blocks are served read-only against that token. Short TTL because the recipient is actively viewing; re-prompting after idle limits the blast radius of a leaked URL.

### Feedback (`app/api/public/feedback.py`, `session.py`)

Two tables, two shapes. `user_feedback` is freeform product feedback (`POST /feedback` in `feedback.py` creates; the `FeedbackStatus` triage workflow is managed on the console surface, `app/api/admin/feedback.py`). `message_feedback` is per-assistant-message thumbs/comment with a unique `(user_id, message_id)` constraint enforced via `IntegrityError → 409` — its endpoints live in `session.py` (as `/sessions/{id}/messages/...` sub-resources), not `feedback.py`.

### File storage (`app/services/file_storage.py`)

Frontend uploads/downloads directly to/from Alibaba OSS via presigned URLs. The backend **never proxies file bytes** — `FileStorage` only mints URLs. Upload URLs accept any extension — `SESSION_FILE_POLICY.allowed_types` only picks the signed Content-Type, and what a file may *do* afterwards is decided where it is used (the inline-preview allow-list); download URLs embed a ``response-content-disposition`` override so the cross-origin OSS response forces a save-as with the real filename. **Authorization differs by direction.** Minting an *upload* URL is JWT-only (+ the per-user file quota) — the object isn't bound to a session yet. *Download* authz is two-step: `_get_or_404` (caller owns the session) then `assert_file_belongs_to_session` (a `session_files` lookup) — so `session_files` **is** the per-key ownership index, and a probe can't mint a URL for another user's `file_key` against a session it owns (403 on the second check). The UUID-unguessable key + short presigned-URL TTL are defense-in-depth on top; the public share download surface (`/shares/{token}/files/download-url`) applies the same `session_files` binding check against the share's session.

The `session_files` table (`app/models/session_files.py`) is the first-class binding between an OSS `file_key` and a session — the durable index behind the user's cross-session **file library**, served at `GET /sessions/files` (filtered + paginated **server-side** by `origin` / `kind` / search, so totals can't drift from the page). Each row carries an `origin` tag (`UPLOAD` user-provided, `DELIVERABLE` agent-produced, `INTERNAL`) and **denormalized** `filename` / `mime_type` / `size_bytes` so the library lists without round-tripping OSS. "kind" (document / image / video / audio / …) is **not a stored column** — it's a SQL CASE expression (`file_kind_case` over `mime_type` + `filename`, valid buckets in `FILE_KINDS`, both in `app/common/file_kind.py`) built into the query so the same classification drives the filter and the response.

**Orphan-upload reaping** (`oss_orphan_tagging_enabled`, default **off**): a presigned upload that's never bound to a session (user abandons the attachment) leaves a paid OSS object with no `session_files` row. When enabled, `generate_upload_url` signs an `x-oss-tagging: lifecycle=orphan` header into the PUT and returns its value as `tagging_header`; the frontend echoes that exact header (it's signed, so omitting it would 403). On bind, `queue_user_message` clears the tag (`file_storage.clear_orphan_tag`, best-effort + post-commit) so the object survives. A bucket **lifecycle rule** (install via `scripts/setup_oss_lifecycle.py`) deletes objects still tagged `orphan` after ~1 day, so OSS — not a backend cron — does the reaping. The flag stays off until rollout is coordinated: the frontend sends the header **only when the response carries `tagging_header`**, so deploy the frontend first (harmless no-op while off), then add the bucket **CORS `allowed-header` for `x-oss-tagging`** + run the lifecycle script, then flip the flag. Skill bundles don't need this — their OSS upload is bound in the same request, compensated on failure.

### Credits / billing (`app/services/credits/`, `app/workers/`)

PAYG credit ledger in front of the LLM turn pipeline. **Every write to `credit_ledger` / `user.credit_balance` funnels through `credits/_internal.py`** — nothing else touches them directly — which preserves the double-entry invariant `user.credit_balance == SUM(credit_ledger.amount)`. Storage unit is **µ-credits** (1 credit = 10_000_000 µ-credits ≈ $0.01 USD). The µ↔USD peg is invariant at `$1 = 1e9 µ-credits`; the 2026-05 redenomination changed only the credit display denomination (`_MICRO_PER_CREDIT` 1e6→1e7), so stored balances kept their USD value while displayed credit numbers shrank 10×.

Per-turn lifecycle:
1. **Reserve** (`reserve_for_turn`, called inside `queue_user_message`): locks the user row, snapshots the model's rate card onto a `credit_reservation`, debits an estimate sized from the model's `reserve_est_input_tokens` (data-driven per-model p50 — an entry gate + per-user concurrency throttle, **not** a worst-case bound), raises `InsufficientCreditsError` if the balance can't cover it. The rate is **frozen on the reservation** so a config change between reserve and settle never re-prices an open turn (customer-trust property: charged cost == cost shown at start).
2. **Mid-turn enforcement** (`app/workers/budget_enforcer.py`, flag-gated by `budget_enforcer_enabled`): the worker's lease heartbeat reports cumulative usage onto `session_turn.interim_input_tokens`/`interim_output_tokens` (pure token counts — the worker never sees money); the enforcer prices them with the frozen snapshot, projects each user's post-settle balance across their concurrent turns, and stops the worst-overrunning turn via the existing cancel channel when the projection hits the buffer. The turn ends as a normal CANCELLED (billed actuals). Fail-open: enforcer down ⇒ pre-enforcer semantics. Interim columns are telemetry only — settle never reads them. **Why a terminal happened** is `session_turn.termination_reason` (`TerminationReason` StrEnum, plain VARCHAR — descriptive, never drives billing/recovery): the *why* to `status`'s *what*. Every terminal write stamps one (`completed` / `user_cancelled` / `insufficient_credits` / `worker_shutdown` / `model_error` / `timeout` / `empty_output` / `internal_error` / `worker_lost`); the cancel-channel payload carries it (empty ⇒ `user_cancelled`, deploy-order safe) and the `agent.stopped` wire event echoes it so the frontend can say "stopped: out of credits" vs plain cancel. Values mirrored in `agent_worker.infra.database.TerminationReason` — change both repos together.
3. **Settle** (`settle_turn`): posts the actual cost from `session_turn.input_tokens`/`output_tokens` — written by the worker in the same fenced transaction as its terminal status flip, so settle reads durable billing-grade storage, **not** the TTL'd Redis stream (a V1 race that's been removed). Idempotent. `refund_reservation` zeros the hold when usage was never measured (worker crash / lost lease).
4. Cost is three additive factors carried in the snapshot: `α·token_cost + β·turn_seconds + γ·model_fee` (`token_markup`, `credit_per_second_credits`, `model_fee_credits`).

**Two-sided pricing (buy vs sell).** The cost peg above (1 credit ≈ $0.01 of LLM COGS) is the **cost basis**, used to price a turn. Separately, `settings.credit_price_cny` (default ¥0.1/credit) is the **customer-facing RMB sale price** for converting a top-up payment into credits — the domestic-market recharge knob. They are deliberately different: selling at ¥0.1 against a ¥0.072 (≈$0.01) cost basis bakes ~28% margin into the recharge step on top of the per-turn token markup. Only `rates.credits_from_cny` (used by `scripts/topup_credits.py --cny` and any future self-serve payment) touches CNY; **billing/settle/balance never see RMB** — they stay entirely on the µ-credit ledger and the USD cost peg. The internal anchor was intentionally **not** redenominated to RMB: at 93 real users / ¥50万 in real top-ups, a peg change would require migrating live balances (high risk), whereas sell-side pricing achieves "1 credit = ¥0.1" with zero balance migration.

Two trigger paths for settle, push + pull halves of one responsibility:
- **Lazy sweep** (`settle_open_for_user`): user-facing endpoints (`GET /credits/*`, `queue_user_message`) settle that user's open reservations on every hit — covers any user who comes back.
- **Background process** (`python -m app.workers.run`, deployed as the `background` sibling): the `settle_sweeper` polls every 60s (correctness backstop for users who never return — API clients, abandoned sessions, workers that crashed between reserve and the terminal write), and `settle_subscriber` listens on the `settle:notify` pub/sub channel (latency optimization — worker publishes on terminal write, settle fires sub-second). Pub/sub loss is expected and harmless; the sweeper backstops it. The sweeper uses a Postgres advisory lock so exactly one host polls per tick in a multi-node deploy; connection loss auto-releases it.

`apply_topup` (credits paid for or given — a typed `source` on the row: `payment` / `commission_conversion` / `welcome_grant` / `admin`) and `apply_adjust` (signed correction) are the operator- and payment-facing ways to move a balance up, beside the referral and check-in rewards and a settle's refund; all are idempotent on a key. `apply_topup` is driven by the admin `topup_credits` script **and** by the payment webhook (see Payments below). [`docs/credits.md`](docs/credits.md) is the single-source design doc for this whole subsystem (read it before changing reserve/settle semantics); [`docs/credits-future.md`](docs/credits-future.md) holds deferred work.

### Payments / recharge (`app/services/payment/`, `app/api/public/payment.py`, `payment_order` table)

Buy-side recharge sitting in front of the credit ledger: a user pays RMB via **汇付斗拱 (Huifu Dougong)** and the ledger is topped up. The ledger layer is **unchanged** — payments only add the order/charge/notify flow and call `credits.apply_topup` exactly once per paid order. Money still funnels through `apply_topup`; the payment layer never writes `credit_ledger` / `user.credit_balance` directly, and `payment_order.ledger_id` back-links the TOPUP row.

- **Provider abstraction**: endpoints/services depend only on the `PaymentGateway` protocol + frozen `ChargeResult` / `VerifiedEvent` dataclasses (`services/payment/provider.py`); the 汇付 impl is `HuifuGateway`. **All 汇付 / `dg-sdk` specifics are confined to `services/payment/huifu.py`** — a second provider is a new adapter + a `PaymentProvider` enum member, nothing else. The SDK is synchronous (`requests`), so `huifu.py` is the one place that bridges sync→async via `asyncio.to_thread`.
- **`payment_order` table** (`app/models/payment_order.py`): worker/backend both backend-owned. UUID PK (opaque in the polled `GET`), `out_trade_no` (UNIQUE, = 汇付 `req_seq_id`) is the provider-facing key. Two **frozen-at-create** amounts: `amount_fen` (RMB cents, integer money) and `credit_micro` (the µ-credit grant via `credits_from_cny` — so a `credit_price_cny` change between scan and pay can't re-price an open order, same trust property as a reservation's `rate_snapshot`). Status `PENDING → PAID / EXPIRED / FAILED`; partial index on `status='PENDING'` over `reconcile_attempted_at` backs the reconciler's round-robin.
- **Four endpoints** (router under `/api/v1/payments/*`): `GET /payments/orders` (JWT, the caller's paid-order history), `POST /payments/orders` (JWT + `@limiter.limit`, gated by `payment_enabled`, freezes credits + places the charge + returns the QR), `POST /payments/webhooks/huifu` (**no JWT** — authenticated by RSA signature over the **raw `resp_data` string** plus its `huifu_id` matching our merchant, since a valid signature proves only that 汇付 sent it; `@limiter.exempt`, returns the exact `RECV_ORD_ID_…` ack but only after a durable write so a failure lets 汇付 redeliver), `GET /payments/orders/{id}` (JWT poll — a read, returning the stored status; only the reconciler moves an order out of `PENDING`).
- **Idempotency** (汇付 notify is at-least-once, 3× retry): the webhook `SELECT … FOR UPDATE`s the order, guards `PENDING → PAID` once, and `apply_topup`'s `idempotency_key="hf:"+out_trade_no` blocks a double credit. The webhook and the reconciler share `_topup_key` + `_grant_paid`, so the two settle paths can't double-grant even if both fire.
- **Reconciler** (`app/workers/payment_reconciler.py`): pull backstop for a lost notification, mirroring `settle_sweeper` (own `pg_try_advisory_xact_lock` key `b"PAYRECON"`, per-row sessions, folded into the same `python -m app.workers.run` process). Applies the provider's verdict — settles a `PAID`, fails a `FAILED` — and reaps an order it gives *no* verdict on (still processing, or unreachable) only once the window for that kind of non-answer closes past `expires_at`. `EXPIRED` is decided here and nowhere else, so an order the provider never answered for keeps being asked about instead of dropping out of reconciliation. Every attempt stamps `reconcile_attempted_at`, and the batch is taken least-recently-attempted first.
- **Config** (`config.py`, all default empty/off so dev boots): `payment_enabled`, `huifu_merchant_id` / `huifu_sys_id` / `huifu_product_id` / `huifu_rsa_private_key` / `huifu_rsa_public_key` / `huifu_env` (`prod` | `mertest`) / `huifu_notify_url` (public HTTPS, includes the `/api/v1` root_path), `payment_min_cny` / `payment_max_cny` / `payment_order_ttl_seconds` / `payment_reconcile_interval_seconds`.

### Referral commission / withdrawal (`app/services/commission/`, `app/api/public/commission.py`, `commission_ledger` + `withdrawal_request` tables)

A **separate, withdrawable cash wallet**, distinct from the credit ledger: when an invitee recharges, the inviter earns a commission (`commission_rate`, default 10% of the paid amount). This is real money (a **cash-payable** liability), so it is **not** mixed into `credit_ledger` (prepaid service liability) — it gets its own ledger in **RMB cents (整数分)** that structurally mirrors `credits/` (same `_internal` funnel, row-lock + flush, idempotency, double-entry invariant `user.commission_balance_fen == SUM(commission_ledger.amount_fen)`). `commission_ledger` writes funnel through `app/services/commission/_internal.py` only.

- **`commission_ledger`** (`app/models/commission_ledger.py`): append-only, BigInteger PK, signed `amount_fen`, `kind ∈ {COMMISSION, WITHDRAW, WITHDRAW_REFUND, CONVERT, CLAWBACK, ADJUST}`, `idempotency_key` UNIQUE. `available_at` is the **settlement hold** (set only on `COMMISSION` rows = `created_at + commission_hold_days`, default T+7) — a refund-clawback window. Withdrawable balance = `total − SUM(unmatured COMMISSION)`, computed read-time (`balance.lock_withdrawable_fen` under the user lock). **`withdrawal_request`** (`app/models/withdrawal_request.py`): UUID PK, cash-out requests; funds are debited up front (a `WITHDRAW` row, `ledger_id` back-link) so they can't be double-spent, mirroring `payment_order → credit_ledger`.
- **Accrual is decoupled from the buyer's top-up**: `commission.accrue_for_order(db, out_trade_no=…)` runs **best-effort post-commit** (own transaction, swallows failures) from both settle paths — the webhook endpoint and `reconcile.py` — *after* `apply_topup` commits, so a referrer-side failure can never roll back the buyer's recharge (same posture as `register.py`'s referral reward). Idempotent on `commission:{out_trade_no}`. Reads the referrer from `invite_redemption.referrer_user_id` (NULL for SYSTEM codes → no commission). **No new worker** — accrual is inline, payout is a script, the hold is read-time.
- **Two cash-out exits**: `POST /commissions/withdrawals` (cash payout, debits the wallet → PENDING `withdrawal_request`, operator settles out-of-band via `scripts/process_withdrawals.py --list|--pay|--reject`) and `POST /commissions/conversions` (convert commission → spendable credits at the `credit_price_cny` sale price; the one place two ledgers move together — a `CONVERT` debit + a `credits.apply_topup` in one transaction). Reads: `GET /commissions/balance` (total/frozen/withdrawable + rate), `GET /commissions/transactions`, `GET /commissions/withdrawals`. Money on the wire is yuan (`*_cny`); the service layer works in 分.
- **Config** (`config.py`, default off so dev boots): `commission_enabled`, `commission_rate` (0.1), `commission_hold_days` (7), `commission_min_withdraw_fen` (1000 = ¥10), `commission_min_convert_fen` (100 = ¥1). Errors: `commission_disabled` / `commission_amount_range` / `insufficient_commission` / `withdrawal_not_found`. **Out of scope (v1)**: auto 汇付 代付 payout, clawback of any kind, per-invitee cap, and the frontend (邀请页/返佣余额/提现 UI). The `CLAWBACK` / `ADJUST` kinds are **reserved, not implemented** — no service writes them, and a hand-written `INSERT` would bypass the funnel; the model docstring says what implementing `CLAWBACK` would have to change in the withdrawable-balance sum.

### Skills (`app/api/public/skill.py`, `app/services/skill_bundle.py`, `skill` + `user_skill_preference` tables)

A skill is an uploaded `SKILL.md` bundle (`.zip`, axon SKILL convention) the worker stages into the sandbox at session start so axon's `use_skill` tool can surface it. **Three origins** (`SkillOrigin`, replaced the old `BUILTIN` in commit `465bdba` — deploy the enum-swap migrations with that code):
- `SYSTEM` — always-on core skills the agent auto-selects. `user_id IS NULL`, **hidden from users** (never returned by `/api/skills`), agent/worker-only, operator-managed.
- `OFFICIAL` — platform-published skills a user browses and opts into. `user_id IS NULL`, operator/seed-managed.
- `CUSTOM` — user-uploaded, owner-scoped (`user_id` set), managed via `/api/skills`.

`user_id`/`origin` consistency is a DB `CheckConstraint` (`ck_skill_origin_user_id_consistent`): platform origins must have `user_id IS NULL`, CUSTOM must have an owner — so a CUSTOM bundle can't masquerade as a platform default. Platform-name uniqueness is the partial index `uq_skill_platform_name` (`WHERE user_id IS NULL`).

- **User-facing visibility is `OFFICIAL` + the caller's own `CUSTOM`** — `SYSTEM` is excluded from `list_skills`, `_get_visible_skill`, and the enqueue invocable filter (fixed in `e9d133b`; the old `PLATFORM_ORIGINS` set had leaked SYSTEM into the skills page and is removed — visibility ≠ platform-ownership). The worker/agent catalog still includes SYSTEM.
- **Upload** is one multipart POST; `skill_bundle.py` is the registration-time validator (rejects path traversal, symlinks, missing/unparseable `SKILL.md`, zip bombs) and extracts name + description from frontmatter, mirroring `axon.skills._parse_frontmatter` so backend-extracted metadata matches what the worker rediscovers. Bundles are **immutable** through this surface — editing means re-uploading (clean worker cache key). PATCH only touches picker metadata (name/description) and the caller's own preference row.
- **`display_name` i18n**: a bundle's `SKILL.md` `metadata.display_name` may be a plain string or a `{locale: name}` map. The map persists in `skill.display_name_i18n` (JSONB, `none_as_null` so "no map" is SQL `NULL`); `GET /skills?locale=` resolves the localized name via `app/services/localized_text.py` (the parse/resolve/normalize chokepoint the Connector catalog shares) with `display_name` as fallback. The map itself never leaves the backend; a PATCH rename clears it so explicit edits win. Existing OFFICIAL rows were backfilled by `scripts/archive/backfill_official_skill_i18n.py`.
- **Two questions, two rows**: `skill.status` — `STAGED` / `PUBLISHED` / `RETIRED` — is whether the listing is live, an operator's call, applying to everyone; `user_skill_preference.enabled` (`(user_id, skill_id)`) is whether that user has put it in their composer picker, theirs alone, and **no row means no** — there is no platform-wide default to fall back to. What the model may invoke in a turn is `status = 'PUBLISHED' AND origin = 'SYSTEM'`, plus that turn's explicit picks — written out only in the worker's `skill_repository`. The `SYSTEM` arm is definitional rather than configurable (agent-only skills are never listed and never togglable, so being live *is* being on), and nothing user-facing ever sees a `SYSTEM` row. Nothing else branches on `origin`. **A user's toggle decides whether the composer offers the skill, not whether the model loads it** — an `OFFICIAL` or `CUSTOM` skill reaches a turn only because the user picked it, and a pick is its own authorization, so the toggle does not gate one. `status` does, which is what makes `RETIRED` a kill switch rather than a default nobody is on. New platform listings land `STAGED` (uploading is not publishing); a new `CUSTOM` row lands `PUBLISHED` with no preference row, so it is out of its owner's picker until they turn it on and reachable meanwhile by a request that names it. One per-user quota, not two: uploads at `skill_registration._MAX_SKILLS_PER_USER` (100, a storage bound). There is no cap on how many skills a user may enable — the old 20 bounded per-turn context growth, and once enabling stopped feeding `use_skill` it was rationing something free. This replaced a single `skill.enabled` column that meant three different things by origin; the column is gone.
- **Browsing taxonomy**: `skill.category_id` → `skill_category`, one row per tab on the skills page. Meaningful only on OFFICIAL rows — a CUSTOM upload lives behind the pinned 「个人」 tab and stays NULL. `GET /skills/categories?locale=` returns `[{id, name}]` **in tab order** (published only, `ORDER BY sort_order, id`), and `GET /skills` carries a flat `category_id` per row: the client already holds `{id, name}` for every tab, so grouping is a map lookup rather than a join and the same string sent once per skill. **A `category_id` the client cannot resolve reads as uncategorised**, exactly like `NULL` — an unpublished category keeps its rows so the tab returns intact when it is republished. An empty published category renders an empty tab the client drops on its own; the backend does not filter for members. A separate table rather than an enum because the catalog it groups is itself operator-managed (`scripts/upload_skill.py` seeds official skills with no deploy), and separate from `connector_category` because a shared table would need a scope column every query had to remember. `ON DELETE SET NULL` on the FK: retiring a category must not take the skills in it with it. Assignment is `category_id` on the console's `PATCH /skills/{id}` or `scripts/upload_skill.py --category NAME` (resolved by name, tri-state through `register_platform_skill_bundle` so a re-upload keeps where it was filed).
- **Per-turn selection**: `POST /sessions/{id}/messages` carries `skills: [name, ...]`. `queue_user_message._filter_invokable_skills` drops any the user can't reach (someone else's CUSTOM, hidden SYSTEM, or a listing that is not `PUBLISHED`) — an explicit pick is its own authorization, so the user's toggle is deliberately not consulted, while `status` is — and snapshots the visible rows (id/name/bundle_key) so the worker loads exactly what existed at enqueue time, request order preserved for the worker's reminder list.

### Connectors (`app/api/public/mcp_server.py`, `app/services/mcp/`, `mcp_server` + `mcp_server_catalog` tables)

A Connector is a remote MCP server the user has configured; the worker connects to it per turn and adapts its tools into the agent's catalog. (On the name, see *Connector vs MCP* under Conventions.)

- **Selection is session-level, not per-turn** (changed in `014d4ab` — a message body no longer carries `connectors`). The configuration lives in the **`session_mcp_server`** table (`app/models/session_mcp_server.py`, composite PK, `ON DELETE CASCADE` from both parents), read and written through `app/services/session/connectors.py`. `POST /sessions` accepts an initial `connectors: [id, ...]` (capped at `CONNECTORS_MAX`, the `?connector=` deep link being the one caller that arrives with any) and `SessionDetailResponse.connectors` is what the composer renders its switches from on open. Afterwards it moves **one Connector per request** — `PUT` / `DELETE /sessions/{id}/connectors/{connector_id}`, both idempotent, both 204 — because sending the whole set on every toggle would let two tabs flipping different Connectors overwrite each other, and because a session's *capabilities* have no business on the endpoint that renames it.
- **A table rather than an id array on `session`**, because these point at *live* rows: `ON DELETE CASCADE` from `mcp_server` removes a deleted Connector from every session that had it configured, guaranteed by the database instead of remembered at each deletion path. Not to be confused with `session_turn.mcp_servers` (JSONB, and staying that way) — that is the immutable record of what one turn actually got, where a foreign key would let a later deletion rewrite history. This table is *current intent*; that column is *the record*.
- **The turn snapshot is still resolved at enqueue.** `queue_user_message` reads `session_connectors.configured_ids`, and `_resolve_mcp_servers` re-reads every row by id, keeps the ids that are the caller's **and** still connected, drops the rest silently (a stale switch costs the turn that Connector, not the message), and writes the survivors to `session_turn.mcp_servers`. Ownership is validated where the configuration is written and enforced again here where it is spent. Order is not preserved — the table doesn't keep it and the worker connects by its own rule (failed-last).
- **Connected ≠ configured.** Connecting makes a Connector *pickable*; a session gets only what its switches turned on, and an empty configuration does not query the table at all. This is a pick at all because an attached Connector's tools enter the model's catalog on **every step** of the turn, and the worker stands each one up serially under a single budget.
- **Browsing taxonomy**: `mcp_server_catalog.category_id` → `connector_category`, one row per tab on the connectors page. `GET /connectors/catalog/categories?locale=` returns `[{id, name}]` in tab order; `GET /connectors/catalog` carries a flat `category_id` per entry. Same client contract as the skills taxonomy above, including "an id the client cannot resolve reads as uncategorised" — the reasoning is written out there. Named `connector_category` per the *Connector vs MCP* rule even though the rows carrying the FK live in the legacy-named `mcp_server_catalog`. Only catalog templates are grouped: a user's own `mcp_server` rows live behind the pinned tab. Assignment is `category_id` on the console's `PATCH /connector-catalog/{id}` or `scripts/manage_connector_catalog.py set-category --url URL (--category NAME | --clear)`.
- **Per-tool trimming is separate and persistent**: `mcp_server.disabled_tools` is not snapshotted here — the worker reads it live at connect time, so switching a tool off applies to the next turn without touching queued ones.
- **A Connector URL is attacker-controlled**, so `app/services/mcp/url_guard.py` is a load-bearing security seam, not a validator: `validate_public_url` / `guard_public_url` pre-flight the https scheme and reject hosts resolving to private / loopback / link-local / reserved addresses (169.254.169.254 included), and `guarded_client` closes the TOCTOU window a pre-flight alone leaves open by resolving each host **once**, pinning the connection to that IP, and never following redirects. Build one and hand it to the MCP SDK (probe) or send through it directly (OAuth) — never a bare `httpx2.AsyncClient` against a user-supplied URL. The SDK took a factory until 2.x and takes the finished client now, which is why every caller builds its own.

### Scheduled tasks (`app/api/public/schedule.py`, `app/workers/schedule_dispatcher.py`, `schedule` + `schedule_run` tables)

A standing instruction to run one agent turn on a clock — daily briefings, weekly digests. The dispatcher runs nothing itself: it claims a due `schedule` and calls **`queue_user_message`**, the same function the message endpoint calls. The only thing a scheduled turn carries that a typed one does not is a system reminder, rendered by `app/services/schedule/briefing.py` and stored on `session_turn.reminders`: it tells the model nobody is there to answer a clarifying question, and which zone and instant "today" means (the occurrence, not the moment of a late catch-up enqueue). The worker forwards it like any other turn reminder, so neither `agent-worker` nor `axon` knows schedules exist.

It is one of the background process's standing tasks — no flag, since a scheduled task that silently never fires is not a feature with a switch off — with its own advisory lock (`b"SCHEDULE"`) on the same tick skeleton as the settle sweeper: every host runs it, exactly one wins each tick. The tick interval, the auto-pause threshold and the two caps are **module constants, not settings** (`_TICK_SECONDS`, `_FAILURES_BEFORE_PAUSE` in the dispatcher; `_MAX_ACTIVE_SCHEDULES`, `_MAX_SCHEDULES_PER_USER` in the endpoint). The interval especially: it has to stay under the 15-minute one-shot grace, and a dial whose wrong value silently drops the user's task belongs in code with its reason beside it.

The timezone is validated against the IANA set with `localtime` and `Factory` removed — `ZoneInfo(value)` alone resolves both, and `localtime` is host-relative, which is the exact opposite of the snapshot the column exists to be. That check is still only as good as the API host's tz database, so the dispatcher closes the gap on its side rather than trusting it.

**Recurrence is a closed set of shapes, not cron** (`ONCE`/`DAILY`/`WEEKLY`/`MONTHLY` + a wall-clock time), so users never type an expression and every schedule renders as a sentence. `app/services/schedule/recurrence.py` is the only place a spec becomes an instant, and it is the one module that deliberately does **not** go through `app/common/business_time.py`: a schedule fires in its owner's own IANA zone, **snapshotted on the row** rather than read from the profile at fire time, so a user who travels does not silently move every standing 09:00 report. `day_of_month` spans 1–31, and a month without the chosen day simply does not fire — the cron reading; "last day of month" would be a different feature with its own semantics. `next_run_at` is never accepted from a caller.

**An owner's edit is decided under the row lock, by `app/services/schedule/lifecycle.py`.** The dispatcher settles an occurrence under `FOR UPDATE` and moves exactly `status` and `next_run_at`, so `PATCH` locks the row first and hands it to `apply_owner_edit`, a pure function of the row, the request and `now`. Deciding on an unlocked read once let an edit store a next run on a one-shot the dispatcher had just completed — saved, shown, and never fired. The clock moves only when the recurrence *actually differs* from the stored one, or the schedule is activated: the form resubmits the recurrence it was opened with, and treating its mere presence as a change dropped a due occurrence on every wording fix.

**`schedule_run` stores no execution status.** One row per occurrence the dispatcher acted on; its outcome is the **first turn** of the session it enqueued, reached by join — not `session.status`, which the owner's own later messages in that session move. A copy here would need a synchronisation mechanism, and the losing side of that race is always the copy. What the row does carry is the two things the session cannot know: `scheduled_for` (which occurrence — paired with `schedule_id` in a unique index) and `skip_reason` (why no session exists). Every read of an outcome — the history, the card's latest run, the unread badge — joins it through `_with_outcome` in the endpoint, so they cannot disagree. A history row whose session was deleted keeps its outcome and loses its link.

**The enqueue's own commit carries the dispatcher's writes, and the rollback half is the point.** The session row, the history row and the advanced clock are all staged before `queue_user_message` is called, so one commit makes the occurrence atomic. A transient failure rolls the claim back with everything else and the next tick simply retries — it is still inside its catch-up grace. A terminal refusal (no credits, a tier that no longer resolves, an attachment that cannot be bound) is caught, and a *second* transaction records why and moves the clock on, because retrying would repeat the refusal every 30s until the grace expired. The running-task cap is neither: it is congestion that clears on its own, so it is rolled back and retried like a blip, and recorded `concurrency_limit` only once no further attempt fits the catch-up window. Committing the claim up front would lose these distinctions.

**Late occurrences fire; very late ones are written off.** Two hours of catch-up grace for a recurring schedule (a 09:00 report is still worth delivering at 10:30); fifteen minutes for a one-shot, whose owner picked an instant. That fifteen is not a taste call — it has to outlast the longest gap the dispatcher can leave between ticks, or the process's own failure backoff (capped at ten minutes, and it climbs on exactly the database trouble catch-up exists for) would retire the one-shots it was moments from delivering. A test pins the relationship rather than trusting the comment. Past that the occurrence is recorded `too_late` and the clock fast-forwards. The anchor is `max(occurrence, now - grace)`, and both halves earn their place: no earlier than the occurrence just handled, so it is not handled twice; no earlier than the start of the catch-up window, so the fast-forward skips only what is genuinely stale. Advancing from `now()` alone would jump clean over the most recent occurrence even when it is minutes old — a 09:00 schedule whose process came back at 09:30 on day four would write off day one and land on day *five*, losing a report half an hour late. So an outage costs the deliveries that were stale and no more.

Consecutive failures pause the schedule at `_FAILURES_BEFORE_PAUSE` (3), which stops both halves of a permanently-broken schedule's damage: the repeated notification and the repeated spend. The concurrency cap deliberately does not count — that is congestion, not the schedule's fault. Two other things pause a schedule outright: a one-shot that was *turned away* (it has not had its turn, so `COMPLETED` would lie), and a timezone this process cannot resolve (every path from there runs the recurrence, so the row cannot even be advanced — pausing is what makes it terminal instead of an every-tick traceback).

**The dispatcher is the only `queue_user_message` caller not behind authentication**, which is the one place `user.status` is otherwise enforced — so `_list_candidates` joins `user` and requires `ACTIVE`. Without it a suspended account's schedules keep creating sessions and spending credits daily, accruing unread badges nobody can log in to see. A suspended owner's occurrences are not recorded as skipped either: the point of suspension is that the account stops consuming, and a history nobody can read is not worth writing.

**Two caps, because they bound different things.** `_MAX_ACTIVE_SCHEDULES` (5) bounds standing *spend*; `_MAX_SCHEDULES_PER_USER` (100) bounds *rows*. Both live in the endpoint module. The first alone would not bound the second — a one-shot frees its ACTIVE slot the moment it fires, so a user creating one a day would grow the unpaginated list endpoint without limit.

Unread state lives on `schedule_run.read_at` rather than in a general notification table: v1 has exactly one notification source, and the badge counts only occurrences that reached an outcome (a first turn still running is not news yet). Opening the page acknowledges every settled result, older runs included, but only as the list request observed them: `GET /schedules` returns the ids of the unread occurrences it saw settled, read *before* the schedules themselves, and `POST /schedules/runs/read` marks exactly those — so a result the request saw still running stays news when it finishes, and a page that failed to load marks nothing. Ids, not a timestamp: `terminated_at` is stamped when the worker's transaction starts and becomes visible only at its commit, so a time cutoff cannot say what a listing actually saw. A second source is when to abstract a `notification` table, not before.

**Attachments are kept before the save commits.** Uploads are born tagged for the bucket's ~1-day orphan reaper. A message clears that tag after its commit and may fail quietly, since its turn reads the file at once; a scheduled task may not fire for days, so `schedule/files.replace` clears the tag on every kept attachment *before* the commit and refuses the save (`file_retention_failed`) if storage does. The failure left is the harmless one — an untagged object nothing references.

### Projects (`app/api/public/project.py`, `app/services/project/`, `project` + `project_file` tables)

A project groups a user's sessions under shared instructions and files. A session belongs to at most one (`session.project_id`); it is put there by `POST /sessions` (`project_id`, FULL only — 422 with LITE) or `PATCH /sessions/{id}` (an id moves it in, `null` moves it out, omitted changes nothing — read through `model_fields_set`), and `GET /sessions?project_id=` lists them. Moving a LITE session in upgrades it through `upgrade_agent_type`, the rule enqueue applies. The worker reads the instructions and files when it claims a project session's turn.

- **Deleting a project moves its sessions out; it does not delete them.** Soft-delete the project, then `UPDATE session SET project_id = NULL` for every session pointing at it — soft-deleted ones too — keeping each one's `updated_at`, or every moved session would jump to the top of the recent list. So a live session never points at a deleted project, and no reader of `session.project_id` joins `project` to ask.
- **The `project` row is the project's lock.** Every write that changes what a project holds — deleting it, creating or moving a session into it, adding or removing a file — takes `FOR UPDATE` on it first (`project.ownership.require_owned_project(for_update=True)`), and only then touches `session` rows. Enqueue never locks a project, so the one order cannot form a cycle. `FOR UPDATE` rather than `FOR SHARE` because those paths also write `project.updated_at`, and upgrading a shared lock deadlocks two concurrent moves.
- **`project.updated_at` is the project's own activity** — rename, instructions, a file added or removed, a session created or moved in — not its sessions' messages, so an enqueue never writes a second row. Those writes touch other tables, so `onupdate` cannot see them and they set it explicitly.
- **`project_file` references the object; nothing is copied** — the same posture as `schedule_file`, and safe for the same reason: no path deletes a user's OSS objects. One row per version: a name the project has becomes `max(version) + 1` over every row of that name, deleted ones included, allocated under the project lock; `uq_project_file_project_id_filename_version` is the backstop. **Only the owner adds files** (`UPLOAD`, `SESSION_FILE`): the agent reads a project's files and never writes them. Deleting a file soft-deletes every version of its name. `origin_session_id` is provenance, deliberately not a foreign key — it must outlive the session, and `SET NULL` would break `ck_project_file_origin_session_consistent`.
- **Adding a file** (`project.files.add`) checks the source's ownership — an upload through `assert_files_owned_by`, a session file as the download endpoint does (404 for the session, 403 for the binding) — refuses a new name past `_MAX_FILES_PER_PROJECT` (100, `project_file_limit`; a new version is never refused), stores OSS's size, and clears the orphan tag **before the commit, after every refusal**, failing the add if storage refuses, as a schedule attachment does.
- **`project_file` is a key-holding table.** `assert_files_owned_by` reads it (deleted rows included) beside `session_files` and `schedule_file`, so a key held only by a project cannot be bound by another user; the upload quota counts its rows (a `SESSION_FILE` outlives its session) per object while the file and its project are live. Any further table that holds keys has to join both.
- **`project.icon` is a name from the client's catalog**, NULL until the owner picks one (the client then draws its default). The schema checks only its shape (lowercase kebab-case, ≤32), so adding an icon is a frontend-only change.
- Caps are module constants, as schedules' are: `_MAX_PROJECTS_PER_USER` (100 live, `project_limit`) and `_MAX_FILES_PER_PROJECT`. Errors: `project_not_found`, `project_file_not_found`, `project_limit`, `project_file_limit`.

### Daily check-in (`app/api/public/check_in.py`, `app/services/check_in.py`, `check_in` table)

One credit reward per user per business-day (`settings.checkin_timezone`, Asia/Shanghai). `check_in` is append-only audit (`UNIQUE(user_id, check_in_date)` is the DB-enforced at-most-one-per-day invariant), `check_in_date` a `DATE` computed by the service in the business tz (not a UTC `now()` default). The reward amount is **not** stored on the row — it lives in the paired `CHECKIN` `credit_ledger` row (money lives in the ledger, same posture as `invite_redemption`), reached via `ledger_id`; the credit grant is idempotent behind that. `streak_day` is a write-time snapshot of the consecutive-day count so the "已连续签到 N 天" display never needs a gaps-and-islands scan. Config: `checkin_reward_credits`, `checkin_timezone`.

### Published sites (`app/models/session_site.py`, `session_site` table)

A static site published from a session via the agent's `publish_site` tool. The **worker** inserts one row per successful publish (after the files land in the OSS preview bucket), keyed by an unguessable 16-char base36 `slug` that doubles as the publish **subdomain label** and the **OSS key prefix** (`{slug}/...`). The public URL `https://{slug}.{preview_domain}/` is *derived* from `slug`, never stored, so a domain change can't strand a column. `user_id` is denormalized from the session owner (immutable) so "my published sites" is a single indexed scan. Backend owns the schema; the worker owns the rows (same split as `sandbox`/`session_context`).

### Organizations (`app/models/organization.py`)

Identity layer only, not yet the billing layer. Registration auto-creates a `PERSONAL` org per user (`OWNER` role). `TEAM` kind and `ADMIN`/`MEMBER` roles exist in the enums so future B2B multi-member work drops in without a migration, but are unused today — the credit ledger still attaches to `user_id`. Keep these two tables (`organization`, `organization_member`) narrow; new concerns (plans, SSO, avatars) get their own tables when actually needed.

### `message.blocks` shape

JSONB list of discriminated blocks. Block types: `text` (USER has `files[]`, ASSISTANT has plain text), `tool_use`, `tool_result` (paired by `tool_use_id`), `error`. Blocks are **immutable** after insert; there are no status/is_error discriminators — a `tool_use` without a matching `tool_result` means the tool never returned (cancelled, crashed, or session died). See `README.md` for the full schema and edge cases.

## Conventions

- **The API layer is two symmetric surface packages**: `app/api/public/` (customer API → `app.public_main`, `/api/v1`) and `app/api/admin/` (operations console → `app.admin_main`, `/admin/api/v1`). A surface earns a package because it is a *trust boundary* — its own token class, gate, CORS, process — not because it is a feature; a third surface would be a third sibling, never a subdirectory. Each surface holds one module per resource directly in the package (no inner `endpoints/` level — inside a named surface, everything is an endpoint module except `router.py`/`dependencies.py`, which name themselves) and a `router.py` the ASGI app mounts as its single router. Surface-agnostic request deps (`get_db`, `get_redis`…) stay at `app/api/dependencies.py`. `schemas/` and `services/` are **not** surface-split — services are shared by both surfaces (the admin rule: call the domain service, never re-implement it), so the `schemas/` root belongs to the public surface and `schemas/admin/` to the console.
- Endpoint files keep inline DB queries; only non-trivial logic moves to `app/services/`. Session-service submodules (`enqueue`, `streaming`, `title`, `recovery`) are re-exported through `app.services.session.__init__` so callers write `from app.services.session import queue_user_message`. Helpers with more than one caller but no single canonical verb (`session/connectors.py`) and internal ones (`session/files.py`) are imported by module path instead. Session refusals are ordinary `AppError`s in `app/errors.py` like every other domain's — there is no session-local exception family to translate.
- `app.public_main` imports `setup_logging` **before** any other app imports so loguru captures module-level loggers.
- Pagination helper (`app/common/pagination.py`) clamps page/page_size to ≥1; list endpoints build one shared filter and apply it to both the count and row queries so totals can't drift from the page.
- **"Today" comes from `app/common/business_time.py`, never from `date.today()` or a UTC `now()`.** Every user-visible day boundary — the daily check-in, the console's dashboard buckets, revenue reporting — is cut in `settings.checkin_timezone` (Asia/Shanghai), because the same event landing on different days depending on which feature asked is a reporting bug you find in a quarterly number. The setting keeps its check-in name (renaming a live config key isn't worth the churn); what matters is that this module is the only place it's read.
- **Anything genuinely shared by both surfaces sits at the `app/api/` root**, not in either package: `dependencies.py` (`get_db`, `get_redis`…) and `uploads.py` (`read_capped`, the chunked multipart reader that bounds peak memory at the cap — a skill bundle arrives the same way whether a user or an operator sends it, and the cap must be enforced identically on both).
- **Connector vs MCP.** Two names for two things, and they do not overlap. A *Connector* is what the user configures and manages — it names the URL surface (`/connectors/*`), every request/response schema (`ConnectorCreate`, `ConnectorResponse`), every `error_type` the frontend localizes (`connector_*`), and everything the UI says. *MCP* is the protocol and the server on the other end — it names the client, the transport, the probe, and the OAuth machinery in `app/services/mcp/` (the browser half of a grant — start, complete, release — is `mcp/authorization.py`; the endpoint module keeps only HTTP). Connector-domain rules — the catalog, ownership, URL identity — live in `app/services/connector/`. New code picks by which of the two it is about, not by which file it sits in. The legacy exceptions are all named after the `mcp_server` table rather than what they serve: that table and `mcp_server_catalog` (renaming a live table is not worth it), the join tables keyed on it — `session_mcp_server` / `schedule_mcp_server`, models `SessionMCPServer` / `ScheduleMCPServer` — and `app/api/public/mcp_server.py` + `app/schemas/mcp_server.py`. None is precedent — a new endpoint, schema or table serving Connectors is `connector*`.
- Exception handlers (`app/exception_handlers.py`) cover `AppError`, `IntegrityError`, `SQLAlchemyError`, `HTTPException`, `RequestValidationError`, and a catch-all `Exception`. Raise `AppError` subclasses (from `app/errors.py`) inside services rather than `HTTPException` — the handler converts them to a uniform JSON shape.
- **A new ASGI surface is `app/asgi.py:create_app`, never a hand-assembled `FastAPI()`.** It installs the limiter, the error handlers, the middleware in the one order that works (SlowAPI inside CORS inside request-id), observability and the health probes. Anything that must hold across surfaces goes in there; anything that legitimately differs becomes an argument.

## Environment variables

Required in `backend/.env`: `db_uri` (PostgreSQL, `postgresql+psycopg://...`), `secret_key` (JWT), `redis_url`, `llm_base_url`, `llm_api_key`, `oss_access_key_id`, `oss_access_key_secret`. `session_tier_models` (maps the UI tier `FAST`/`STANDARD`/`ADVANCED` → the `model_id` written to `session.model_id`) and `supported_session_model_ids` (the whitelist the resolved `model_id` is checked against) have defaults in `config.py` — keep both in sync with `agent-worker/models.toml`, since a mismatch surfaces as a worker-side `ValueError` on the next turn rather than at session creation. Alibaba DirectMail creds (`aliyun_dm_*`) and Aliyun SMS creds (`aliyun_sms_*` — `access_key_id`/`access_key_secret`/`sign_name`/`template_code`/`region`, for the phone-OTP channel) default to empty strings so dev boxes without provider access still boot.

MCP Connectors (`app/services/mcp/`, `app/api/public/mcp_server.py`): `mcp_credential_encryption_key` (a Fernet key — generate with `Fernet.generate_key()`) encrypts Connector credentials and OAuth tokens at rest and **must be byte-identical to the worker's `mcp_credential_encryption_key`**, or the worker can't decrypt what the backend sealed. Empty default still boots, but create/probe fails loudly the moment a credential needs sealing (any BEARER/HEADER/OAUTH Connector). OAuth Connectors additionally need `mcp_oauth_redirect_uri` — the public `{app origin}/api/connectors/oauth/callback` (the frontend serves that proxy route; register it with manual OAuth apps) — empty ⇒ the authorize step fails with a 500 `oauth_not_configured` and a log line naming the setting, while none/bearer/header Connectors keep working; `mcp_oauth_state_ttl_seconds` (default 600) bounds the pending-authorization Redis state. `mcp_client_metadata_url` (optional) enables **CIMD** — the URL itself becomes our `client_id` and the authorization server fetches it, so no per-Connector registration is stored; it must be https with a non-root path and must resolve to this API's `GET /api/connectors/client-metadata` (public + rate-limit exempt, since the fetch comes from the provider). Unset ⇒ dynamic client registration, which stays the fallback for servers that don't advertise CIMD. Ships ten `mcp_server` alembic migrations (plus the `session_turn` snapshot one) — run `alembic upgrade head` before serving, and before deploying the worker, which reads and writes the whole grant. **This module obtains grants; it does not renew them.** Renewal is the worker's, on demand during a turn (`agent-worker/agent_worker/infra/connector_grant_rotation.py`), because a turn can outlive its access token — Atlassian issues one-hour tokens against a one-hour `max_execution_time` — and no look-ahead window closes that gap. A refresh token is single-use, so exactly one party may spend it; what guarantees that across N worker replicas is a claim written on `oauth_refresh_after`, not there being a single writer process. What stays here is the browser flow — authorize, exchange, and the RFC 7009 revocation that ends a grant — in `app/services/mcp/authorization.py`. **Disconnecting an OAuth Connector gives the grant up rather than shelving it**: the tokens are cleared and an RFC 7009 revocation is sent to the provider after the response (best-effort — our copy is gone either way), so reconnecting means authorizing again. What survives is the row and its client registration, which is the whole difference from deleting it; the other auth types keep their credential, because the user typed it and it is not ours to throw away. Renewing a grant for a disconnected row would be maintaining access the user believes they ended, so the worker's claim query filters on `connected` too.

Admin console (all defaulted in `config.py`): `admin_cors_origins` (its own allowlist, default `http://localhost:3400` — never inherits `cors_origins`), `admin_access_token_expire_minutes` (default one workday vs the customer token's week, because the console is the highest-privilege surface), `rate_limit_admin_login` (default `5/minute` per IP — tighter than the customer login, since the operator pool is tiny and known). It shares `secret_key` and `db_uri` with the public API.

Credit/quota knobs (all defaulted in `config.py`, edit-and-restart for V1): `credit_rates` (per-model rate card — one entry per `supported_session_model_ids` model, else reserve fails for that model), `credit_per_second_credits` (β infra fee), `credit_reserve_max_turn_seconds` (the duration a hold is sized for) / `credit_reserve_max_input_tokens` (the input estimate for a model whose rate card carries no `reserve_est_input_tokens`; settle uses actuals), `credit_welcome_grant_credits` (auto-grant on registration), `max_concurrent_running_tasks` (per-user RUNNING-session cap, default 10), `checkin_reward_credits` / `checkin_timezone` (daily check-in). Skills use `oss_skill_bucket_name` (separate OSS bucket for bundles). See `config.py` for the full `Settings` model.
